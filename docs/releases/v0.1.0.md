# ChainSentinel 0.1.0 (pre-release)

First published version of ChainSentinel, the self-hosted blockchain intelligence and alerting platform (repository
`openchain-intelligence`, technical prefix `oci`). Released from `main` at commit `5f581fe` plus the release preparation
commit; CI green on `5f581fe` (run of 2026-11-10).

This is a **0.x pre-release**: the REST API v1 and the rule schema `openchain.io/rule/v1` may still change before 1.0,
and every breaking change will be listed in [`CHANGELOG.md`](../../CHANGELOG.md). Read the known issues below before
using it on real chains.

## What it does

- Indexes **Ethereum and TRON** itself (native and token transfers, approvals, stablecoin freezes, contract admin
  changes), with RPC failover and resumable indexing checkpoints (an indexer restarts where it stopped, within 7,200
  blocks).
- Profiles every wallet it sees and runs **detectors** that explain each signal with the transactions behind it; risk
  scores are traceable to their contributions.
- Turns **YAML rules** (`openchain.io/rule/v1`) into alerts delivered to webhooks (signed), Slack, Discord and Telegram,
  with an outbox, retries and dead letters.
- **Console** (Angular): overview, explorer, wallet dossier with fund flow graph, alerts inbox, rules, watchlist,
  settings; public landing page on `/`.
- Runs on your own machine or server with Docker Compose; PostgreSQL stores alerts, rules, labels, keys, connectors,
  watchlist and indexing checkpoints (Flyway migrations `V1` to `V9`, applied automatically).

The complete list is in the `[0.1.0]` section of the changelog.

## Install

New installation only (no earlier release exists): follow the README, "Step 3 — Try the demo" then "Step 4 — Run it
for real". Images are built locally by `docker compose up --build` and tagged `0.1.0`.

If the release workflow is enabled for this release, the images are also published as
`ghcr.io/alertmanager12-blip/openchain-intelligence-app:0.1.0` and
`ghcr.io/alertmanager12-blip/openchain-intelligence-frontend:0.1.0`, with a CycloneDX SBOM for each image attached to
the GitHub release.

## Known issues

Verified in the code of this version on 2026-11-13. They are fixed or mitigated on the development branch and planned
for 0.2.0; the fixes are **not** in 0.1.0.

**Correctness of results**

- **Chain reorganisations are not retracted from the intelligence layer.** A transfer whose block leaves the canonical
  chain stays in wallet profiles, signals and risk scores (only freezes and rule-engine windows are reverted; alerts are
  annotated). Indexing reads confirmed blocks only (12 on Ethereum, 19 on TRON), so this is rare.
- **Transfers of unverified token contracts feed the behavioural detectors.** Exposure ignores fake tokens and dust, but
  fast forwarding, circular flow, unusual amount, fan-out and estimated draining can be triggered by worthless tokens
  sent between third-party addresses.
- **Indirect exposure can be missed** when an intermediary paid the wallet several times: the trace keeps the oldest
  payment of each sender.
- **A non-zero amount below the displayed precision is shown as "0"** in the console (a dust transfer can disappear
  from view).

**Operations**

- **Memory is not bounded at chain-wide volume.** Wallet profiles, signals and scores live in memory and are rebuilt
  after a restart; at full Ethereum + TRON volume the working set grows by several hundred megabytes per hour. Plan
  memory, or index fewer networks.
- **The indexing lag shows 0 when the provider is failing** (head unknown): the metric `oci_indexer_lag_blocks` and
  `GET /api/v1/networks` report "no lag" exactly when indexing has stopped.
- **JSON-RPC rate-limit errors returned with HTTP 200** (for example `-32005`) are not retried and do not trigger
  failover; provider responses are read without a size limit.

**Security**

- **The console and its API proxy listen on every interface** (`"4200:8080"` in `docker-compose.yml`), in plain HTTP.
  On a server, put it behind a reverse proxy with TLS, or change the mapping to `"127.0.0.1:4200:8080"`.
- **With OIDC enabled:** the token audience is checked only when `OCI_SECURITY_OIDC_AUDIENCE` is set (set it), and an
  API key sent as `Authorization: Bearer oci_…` is refused (send it in `X-API-Key`).
- **Single organisation:** no multi-tenancy, no API rate limiting.
